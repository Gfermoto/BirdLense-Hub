# Расследование спама «App is UP!» в Telegram

## Первопричина (найденная)

Сообщение «App is UP!» отправляется при вызове `create_app()` — то есть при **каждом запуске процесса, который загружает приложение**. Это происходит:

1. **При старте контейнера** — один раз (gunicorn worker загружает `app:app`).
2. **При перезапуске воркера gunicorn** — если воркер умер (timeout, crash, OOM), новый воркер снова вызывает `create_app()`.
3. **При перезапуске контейнера** — entrypoint выходит с кодом 1, Docker перезапускает контейнер по `restart: unless-stopped`.

### Главная причина спама: таймаут health check в entrypoint

В entrypoint скрипт ждёт готовности API **не более 30 секунд**. Если за 30 секунд gunicorn не начал отвечать на `/api/ui/health`, скрипт делает `exit 1` → контейнер завершается → Docker перезапускает контейнер → снова «App is UP!».

Но **gunicorn не отвечает, пока не завершится `create_app()`**. Внутри `create_app()` вызывается `notify_app_startup()` → `notify()` → отправка в **Telegram** (таймаут по умолчанию **45 секунд**). То есть при медленной сети или нагруженном API Telegram первый ответ API может прийти позже 30 секунд. В итоге:

- за 30 секунд health check не успевает;
- entrypoint выходит с ошибкой;
- контейнер перезапускается;
- новый контейнер снова шлёт «App is UP!» и снова не успевает за 30 с → цикл перезапусков и спам.

**Исправление:** в entrypoint время ожидания health check увеличено с 30 до **60 секунд** (60 попыток по 1 с). Этого достаточно, чтобы уложиться в типичный `telegram_timeout` (45 с) и остаться в пределах ожидания.

## Дополнительные меры

1. **Маркер в `/tmp`** — после первой отправки создаётся файл `/tmp/.birdlense_startup_notify_sent`. Повторные вызовы `notify_app_startup()` (например, после перезапуска воркера в том же контейнере) отправку пропускают. Маркер создаётся **до** вызова `notify()`, чтобы при сбое во время отправки следующий старт не слал сообщение снова.

2. **Диагностика в логах** — при каждом вызове пишется:
   - `create_app() invoked (pid=...)` — факт загрузки приложения (новый процесс/воркер);
   - `notify_app_startup: sending (pid=...)` — решено отправить «App is UP!»;
   - `notify_app_startup: skip (marker exists, pid=...)` — отправка пропущена, т.к. маркер уже есть;
   - `notify_app_startup: skip (restart processor, pid=...)` — пропуск из‑за недавнего «Перезапустить процессор» из UI.

По ним можно понять, как часто реально вызывается `create_app()` и отправляется ли уведомление.

## Как проверить у себя

1. **Счётчик перезапусков контейнера:**
   ```bash
   docker inspect birdlense --format '{{.RestartCount}}'
   ```
   Если число растёт каждые 1–2 минуты — контейнер действительно перезапускается (например, из‑за таймаута health check в entrypoint до исправления).

2. **События Docker:**
   ```bash
   docker events --filter container=birdlense
   ```
   Оставьте на 2–3 минуты; по `die` и `start` видно цикл перезапусков.

3. **Логи приложения:**
   ```bash
   docker logs birdlense 2>&1 | head -100
   ```
   Ищите:
   - повторяющиеся строки `create_app() invoked (pid=...)` — значит, процесс приложения (воркер) стартует заново;
   - `API health check failed after 30s` (в старых образах) — подтверждение выхода entrypoint по таймауту;
   - `Worker timeout` (gunicorn) — воркер убит из‑за долгого запроса (по умолчанию 30 с).

4. **Таймаут воркера gunicorn** (по умолчанию 30 с): если какой‑то HTTP‑запрос обрабатывается дольше, gunicorn убивает воркер и поднимает новый → снова `create_app()` и при отсутствии маркера — повторная отправка. После правок маркер создаётся до отправки и переживает перезапуски воркера в рамках одного контейнера, поэтому повторных отправок из‑за этого быть не должно. При необходимости можно увеличить таймаут воркера в команде gunicorn (например, `--timeout 60`).

## Итог

- **Первопричина спама:** слишком короткое ожидание health check в entrypoint (30 с) при возможной задержке отправки в Telegram (до 45 с) → выход entrypoint → перезапуск контейнера → повторная отправка «App is UP!».
- **Что сделано:** ожидание увеличено до 60 с; маркер создаётся до `notify()`; добавлено логирование для последующей диагностики.
