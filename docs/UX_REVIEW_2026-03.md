# Консилиум: UX, логика и юзабилити BirdLense Hub

**Дата:** 15 марта 2026  
**Повод:** Запрос на независимую оценку трёх проблем: виджет «Последняя птица», слияние детекций, обработка «Bird» как вида.

---

## 1. Виджет «Последняя птица сегодня»

### Текущая логика
- Запрос: `SpeciesVisit` за день, `order_by(start_time.desc()).first()`
- Показывается визит с **самым поздним start_time**

### Оценка UX-дизайнера
**Проблема семантики:** Пользователь ожидает «последнюю увиденную птицу» = последнее по времени наблюдение. Сейчас берётся визит с самым поздним **началом**. Если визит длинный (9:50–10:05), а другой короткий (10:02–10:03), логичнее считать «последней» ту, что закончилась позже.

**Рекомендация:** Использовать `order_by(SpeciesVisit.end_time.desc())` или `greatest(start_time, end_time)` — «последняя» = последнее по времени наблюдение.

### Оценка продукт-менеджера
**Кейс «только одна птица»:** Если за день одна детекция (9:53), надпись «Последняя птица сегодня» звучит странно — она и первая, и последняя. Варианты:
- «Последняя птица сегодня» (оставить)
- «Последняя птица: 9:53 — Eurasian Jay» (без «сегодня», если контекст ясен)
- Добавить «Последние 3 птицы» — карточки с последними N визитами

### Оценка инженера
Код корректен: `start_time.desc()` даёт визит с самым поздним началом. Возможная путаница — **часовой пояс**: если UI в локальном времени, а БД в UTC, 9:53 UTC = 12:53 МСК. Проверить отображение времени.

## 2. Слияние детекций (merge)

### Текущая логика
- **merge_window_seconds: 5** — окно для MQTT-событий
- **dedup_window_seconds: 45** — детекции одного вида с разрывом > 45 сек = разные визиты
- **VisitProcessor.visit_timeout: 60** — визиты в БД объединяются, если разрыв < 60 сек

### Оценка инженера данных
**Риски:**
1. **Разные окна:** Processor merge (45 сек) vs VisitProcessor (60 сек) — несогласованность. Один слой может разъединить то, что другой объединил.
2. **MQTT перезаписывает интервал:** При слиянии MQTT с YOLO: `_merge_into(merged, conf, 0, video_duration)` — MQTT-событие растягивает интервал на всё видео. Одно событие Frigate «Eurasian Jay» в 9:53 может превратить короткий YOLO-трек (9:52–9:54) в «9:50–10:00».
3. **Один MQTT на вид:** `by_key[(key, -1)]` — все MQTT-события одного вида в одном видео сливаются в одну запись. Несколько прилётов одной сойки за 60 сек видео → один «визит».
4. **Перебор при поиске merge:** В YOLO-цикле `for k, det in list(by_key.items())` — берётся **первый** подходящий визит. При нескольких визитах одного вида порядок может быть неоптимальным.

### Оценка орнитолога
**Реалистичность:** 45 сек — разумный порог для «один визит»: птица улетела и вернулась через минуту — это два визита. Но 45 сек может быть мало для кормушки: птица отвлеклась на соседа и вернулась через 30 сек — это один визит. **Рекомендация:** Сделать `dedup_window_seconds` настраиваемым (сейчас в конфиге есть, но 45 — жёстко по умолчанию).

### Рекомендации по слиянию
1. Унифицировать окна: `visit_timeout` = `dedup_window_seconds` или явная связь в конфиге.
2. MQTT: не растягивать на `video_duration`, использовать реальное время события из `timestamp`.
3. Логирование: при merge писать в лог, что с чем объединено (для отладки «много событий в одно»).

## 3. «Bird» как вид vs неизвестный объект

### Текущая логика
- **Frigate:** `species = sub_label or label or "unknown"` — без Bird Classification → `label="bird"` → вид «Bird»
- **YOLO:** Классификатор возвращает имя класса. Если в модели есть класс «Bird» (generic) — он попадает как вид
- **Unknowns:** Порог по `confidence < 0.5` — низкая уверенность. «Bird» с confidence 0.9 **не** попадает в Unknowns

### Оценка продукт-менеджера
**Проблема:** «Bird» семантически = «птица, вид не определён». Но система трактует как полноценный вид:
- Попадает в топ видов
- Учитывается в статистике
- Не попадает в «Неизвестные» (если confidence высокий)

**Ожидание пользователя:** Детекция «Bird» (без вида) должна вести себя как «неизвестный объект» — либо в Unknowns, либо отдельная категория «Птица (вид не определён)».

### Оценка орнитолога
«Bird» как вид бесполезен для учёта: нельзя отличить синицу от воробья. Для науки и eBird нужны виды. **Рекомендация:** «Bird» и «bird» считать «Unknown species» — не включать в топ, показывать в Unknowns или отдельном блоке «Требуют определения».

### Рекомендации
1. **Фильтр «Bird»:** Не создавать Species «Bird» из Frigate label, или помечать `active=False` и не считать в overview.
2. **Unknowns:** Добавить правило: `species_name in ('Bird', 'bird')` → всегда в Unknowns (или отдельная вкладка «Птица без вида»).
3. **Конфиг:** `detection.generic_bird_as_unknown: true` — «Bird» не участвует в статистике, только в Unknowns.

## Дополнительные юзеркейсы

### Кейс: «Утро, открыл приложение»
Пользователь хочет быстро понять: кто был, когда, какая погода. Виджет «Последняя птица» должен отвечать на «кого я видел последним». Сейчас — ок, если `start_time` ≈ `end_time`. Иначе — см. п.1.

### Кейс: «Много соек за час»
Несколько визитов Eurasian Jay. Ожидание: несколько карточек в Timeline. Риск: merge объединяет в одну из-за dedup_window. Нужны настраиваемые окна и прозрачность (логи).

### Кейс: «Исправить вид в Unknowns»
Contributor видит «Bird» с 0.6 confidence — не в Unknowns (порог 0.5). Но «Bird» — по сути unknown. Решение: «Bird» всегда в Unknowns или в отдельном блоке.
