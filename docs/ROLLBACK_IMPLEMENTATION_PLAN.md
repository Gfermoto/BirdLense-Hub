## 1. Критическое ревью документа

### 1.1. Точность и актуальность

| Аспект | Оценка | Замечание |

### 1.2. Полнота и непротиворечивость

- **П. 1 (nginx):** рекомендация корректна. В `standalone.conf.template` до сих пор `proxy_pass http://__GO2RTC_UPSTREAM__$uri$is_args$args` — риск 500 в части окружений. Замена на `proxy_pass http://__GO2RTC_UPSTREAM__;` после rewrite — одна строка, поведение для клиента то же.
- **П. 2 (get_go2rtc_upstream):** при падении чтения конфига (оба файла недоступны или битый YAML) скрипт может выбросить исключение до `print('127.0.0.1:1984')`. Глобальный try/except с fallback — правильная рекомендация.
- **П. 3 (entrypoint):** обрезка `\r\n` — без споров. Нефатальный health check документ правильно помечает как «по желанию»: контейнер тогда не падает при мёртвом API, но оркестратор будет считать его здоровым — решение под вашу политику деплоя.
- **П. 4 (BIRDLENSE_PORT):** для текущей установки не обязательно: снаружи порт задаётся через `${BIRDLENSE_PORT:-8085}:8080`, внутри nginx слушает 8080. Имеет смысл только если понадобится менять порт внутри контейнера без правки compose.
- **П. 5 (MJPEG-fallback):** описан аккуратно (без фоновых MJPEG по всем камерам). Для установки, где go2rtc стабилен в сети, приоритет ниже.
- **П. 6 (Intel GPU):** большой блок (6.1–6.3) — полезный справочник для будущего. Сейчас на сервере нет Intel NUC с VA-API, раздел не применим к текущему деплою. Противоречий с п. 1–5 нет.

### 1.3. Безопасность и эксплуатация

- **Без privileged и host (п. 6.2):** соответствует текущему compose (нет `privileged`, нет `network_mode: host`). Рекомендации уместны.
- **Healthcheck в compose:** в документе (п. 6.3) предложен healthcheck для приложения (`/api/ui/health`), но в `app/docker-compose.yml` его нет. Добавление даст Docker и оркестраторам возможность считать контейнер нездоровым при падении API — разумное улучшение.
- **restart: unless-stopped:** уже есть в compose — ок.
- **Лимиты CPU/памяти и read_only (п. 6.3):** описаны как усиление безопасности. Для пошагового плана их можно вынести в отдельную фазу после стабилизации базовых пунктов.

### 1.4. Дублирование и навигация

- Блок «Стабильность кода» и подраздел «Как избежать поломок при работе с AI» в п. 6.3 частично пересекаются. Ссылка из «Стабильность кода» на 6.3 снимает дублирование; оставить как есть приемлемо.
- В начале документа нет краткого «Текущий статус реализации» (что уже сделано по пунктам 0–7). Это усложняет использование документа как чек-листа. Рекомендация: добавить в ROLLBACK_LOST_FEATURES.md короткий подраздел со статусом.

### 1.5. Итог ревью

- Документ в целом **корректен и применим** к установке: учтена сеть с go2rtc/MQTT/HA/ESPHome, деплой и данные на сервере.

### Фаза 4 — Intel GPU (реализовано: выбор CPU / Intel GPU)

- **Ориентация:** любая платформа Intel со встроенной графикой (в т.ч. NUC, Celeron).
- **Реализовано:** в настройках Видео — выбор кодирования записи: **CPU** или **Intel GPU (встроенная)**. Конфиг: `video.encoding: cpu | intel`. При `intel` процессор использует FFmpeg с VA-API (`-hwaccel vaapi`, `h264_vaapi`); если `/dev/dri/renderD128` недоступен — автоматический откат на CPU.
- **Для работы Intel GPU:** в compose добавить `devices: - /dev/dri/renderD128:/dev/dri/renderD128`, на хосте — драйверы (см. ROLLBACK_LOST_FEATURES.md п. 6.1). Без проброса устройства выбор «Intel GPU» в UI просто даёт запись на CPU (с предупреждением в логах).

### Фаза 5 — Ужесточение безопасности (опционально, после стабилизации)

- Лимиты ресурсов в compose (`deploy.resources.limits`: cpus, memory).
- Read-only rootfs + точечные volume для записи (если приложение не пишет вне смонтированных каталогов).
- Запуск от непривилегированного пользователя в Dockerfile (особенно актуально при добавлении GPU и проброса устройств).

Вносить по шагам с проверкой после каждого изменения.
