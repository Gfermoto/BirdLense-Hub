# Что потеряли при откате (до GPU) и стоит ли возвращать

После отката к коммиту 5f108c4 (до Intel NUC/VA-API) из кодовой базы исчезли не только GPU-фичи, но и часть правок, которые делали работу стабильнее или удобнее. В этом документе: что именно **потеряли** (и как вернуть без риска), что **не потеряно**, пошаговые рекомендации по Intel GPU по образцу Frigate и советы по стабильности кода. Рекомендации не окончательные — документ можно дополнять.

**Пошаговый безопасный план реализации и ревью документа:** см. `docs/ROLLBACK_IMPLEMENTATION_PLAN.md`.

## Что НЕ потеряно (работает как раньше)

- Сама отправка «App is UP!» в Telegram при старте приложения есть в коде (`notify_app_startup()` в `app/web/app.py`). Чтобы она срабатывала только при перезапуске контейнера (а не при перезапуске процессора), нужна схема из п. **0** (процессор в цикле в entrypoint).
- Остальная логика уведомлений (детекции, тест из настроек, Web Push), API камер, go2rtc в процессоре, настройки — в рамках отката не трогались.

Ниже перечислено то, что при откате **исчезло** из репозитория (правки из откатанных коммитов и сессии отладки).

## 0. Перезапуск процессора без перезапуска контейнера + «App is UP!» только при старте контейнера

**Что было:** 1) При нажатии «Перезапустить процессор» в UI перезапускался только процесс процессора, контейнер продолжал работать. 2) Сообщение «App is UP!» в Telegram уходило только при реальном перезапуске контейнера (docker restart, перезагрузка хоста), а не при перезапуске процессора — иначе был спам.

**Сейчас (реализовано):** В entrypoint процессор запускается в цикле; при выходе (флаг перезапуска или падение) перезапускается только процесс, контейнер не выходит. «App is UP!» уходит только при старте контейнера. Маркер `.startup_notify_skip` при вызове API перезапуска процессора оставлен как страховка.

| Стоит ли возвращать | Да. Иначе контейнер дёргается при каждом перезапуске процессора и спам в TG. |
|---------------------|-------------------------------------------------------------------------------|
| Как сделать         | **Основное решение:** в entrypoint запускать процессор **в цикле** (`while true; do ... python main.py || true; sleep 2; done`). Тогда при выходе процессора (флаг перезапуска или crash) перезапускается только процесс, контейнер не выходит. Gunicorn стартует один раз при старте контейнера → «App is UP!» уходит только при реальном перезапуске контейнера. **Дополнительно (уже есть в коде):** маркер `.startup_notify_skip` при вызове API «перезапустить процессор» + проверка в `notify_app_startup()` — страховка на случай старой схемы без цикла. |
| Не ломает           | Да. Поведение API и UI не меняется; меняется только то, что процессор перезапускается внутри контейнера. |

## 1. Исправление 500 на `/go2rtc/` в nginx

**Что было:** В части окружений nginx отдавал **500 Internal Server Error** на запросы к `/go2rtc/stream.html` из‑за использования переменных в `proxy_pass`:
`proxy_pass http://__GO2RTC_UPSTREAM__$uri$is_args$args;`

**Что делали:** Меняли на вариант без переменных в URI: `rewrite ^/go2rtc/(.*)$ /$1 break;` и `proxy_pass http://__GO2RTC_UPSTREAM__;` (без `$uri$is_args$args`).

**Сейчас:** В коде снова вариант с `$uri$is_args$args` — у тех, у кого раньше был 500, он может вернуться.

| Стоит ли возвращать | Да, если у вас когда‑то был 500 на go2rtc. Риск минимальный. |
|---------------------|---------------------------------------------------------------|
| Как сделать         | В `app/nginx/standalone.conf.template` в `location /go2rtc/` оставить `rewrite ^/go2rtc/(.*)$ /$1 break;` и заменить строку proxy_pass на: `proxy_pass http://__GO2RTC_UPSTREAM__;` (без `$uri$is_args$args`). |
| Не ломает           | Да. Поведение для клиента то же, меняется только способ формирования upstream-запроса в nginx. |

## 2. Устойчивость get_go2rtc_upstream.py

**Что было:** Оборачивали чтение конфига в try/except, при любой ошибке выводили fallback `127.0.0.1:1984`, чтобы entrypoint не получал пустую строку и не подставлял её в nginx.

**Сейчас:** При ошибке чтения YAML или отсутствии файла скрипт может упасть или ничего не вывести → nginx получает пустой upstream → возможны 502 или некорректный конфиг.

| Стоит ли возвращать | Да. Мало кода, меньше сюрпризов при битом конфиге. |
|---------------------|------------------------------------------------------|
| Как сделать         | В `get_go2rtc_upstream.py`: весь код получения `url` обернуть в try/except; в except (или если в конце `url` пустой) делать `print('127.0.0.1:1984')`. |
| Не ломает           | Да. Меняется только поведение при ошибках — всегда будет валидный host:port. |

## 3. Entrypoint: обрезка GO2RTC_UPSTREAM и нефатальный health check

**Что было:**
- Обрезка перевода строки в `GO2RTC_UPSTREAM`: `GO2RTC_UPSTREAM=$(...); GO2RTC_UPSTREAM="${GO2RTC_UPSTREAM//[$'\r\n']/}"`.
- Увеличение таймаута ожидания API (например до 45 с) и при неуспешном health check не делать `exit 1`, а только писать в лог и продолжать (чтобы контейнер не падал, а можно было смотреть логи).

**Сейчас:** При случайном `\n` в переменной или долгом старте gunicorn контейнер может сформировать неверный nginx-конфиг или выйти по таймауту.

| Стоит ли возвращать | Обрезку `\r\n` — да. Нефатальный health check — по желанию (удобно для отладки, но контейнер может «жить» при мёртвом API). |
|---------------------|--------------------------------------------------------------------------------------------------------------------------------|
| Как сделать         | В entrypoint после `GO2RTC_UPSTREAM=$(...)` добавить обрезку. Для нефатального check — заменить `exit 1` на `echo "API health check failed"` и не выходить. |
| Не ломает           | Обрезка — да. Нефатальный check меняет семантику старта (контейнер «успешен» даже без API) — решать по своей политике деплоя. |

## 4. Порт приложения (BIRDLENSE_PORT) в nginx

**Что было:** В шаблоне nginx подставляли порт из переменной окружения (например `listen __BIRDLENSE_PORT__;`), в entrypoint заменяли `__BIRDLENSE_PORT__` на значение (например 8085), чтобы не хардкодить 8080.

**Сейчас:** В шаблоне снова `listen 8080`; снаружи порт задаётся только маппингом в docker-compose (`8085:8080`). Для одного контейнера этого достаточно.

| Стоит ли возвращать | Только если нужен разный порт внутри контейнера без смены compose (редко). |
|---------------------|-------------------------------------------------------------------------------|
| Как сделать         | В шаблоне `listen __BIRDLENSE_PORT__;`, в entrypoint подставлять порт из env (например `${BIRDLENSE_PORT:-8080}`). |
| Не ломает           | Да, при корректной подстановке. |

## 5. MJPEG-fallback в Live (когда go2rtc недоступен)

**Что было:** В API камер добавляли опциональное поле `stream_url_mjpeg` (URL MJPEG от процессора). В UI Live — кнопка переключения «RTC/MSE» ↔ «MJPEG», чтобы при 502 или чёрном экране можно было смотреть хотя бы одну камеру через процессор.

**Сейчас:** Только go2rtc; при 502 или недоступности go2rtc запасного варианта в UI нет.

| Стоит ли возвращать | Имеет смысл, если часто бывает недоступность go2rtc и нужен обходной просмотр. Увеличивает сложность (API, UI, процессор должен отдавать MJPEG по выбранной камере). |
|---------------------|---------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Как сделать         | 1) В процессоре оставить отдачу MJPEG по активной камере (как было). 2) В API камер добавить `stream_url_mjpeg` при наличии MJPEG. 3) В Live — кнопка и переключение iframe/img. Не поднимать фоновые MJPEG по всем камерам (риск падений и нагрузки). |
| Не ломает           | При аккуратном внедрении — нет. Важно не включать лишние потоки в процессоре. |

## 6. Intel GPU (VA-API) для записи и выбор CPU/GPU

**Ориентация:** любая Intel со встроенной графикой (NUC, Celeron, и т.д.), не только NUC.

**Реализовано:**
- В настройках Видео — выбор кодирования записи: **CPU** или **Intel GPU (встроенная)**. Конфиг: `video.encoding: cpu | intel`.
- При `intel` процессор использует FFmpeg с VA-API (`-hwaccel vaapi`, `h264_vaapi`). Если устройство `/dev/dri/renderD128` недоступно в контейнере — запись идёт на CPU с предупреждением в логах.
- Для работы Intel GPU: в docker-compose добавить `devices: - /dev/dri/renderD128:/dev/dri/renderD128`, на хосте — драйверы (п. 6.1 ниже).

**Опционально (не реализовано):** Dockerfile.intel, отдельный compose, метрики загрузки GPU в System (intel_gpu_top / sysfs).

| Стоит ли расширять | Выбор CPU/GPU уже есть. Метрики GPU и отдельный образ — по желанию. |
|--------------------|---------------------------------------------------------------------|
| Как включить Intel | Настройки → Видео → Кодирование записи: Intel GPU. Проброс устройства в контейнер — см. п. 6.1. |
| Не ломает          | Да. Без проброса `/dev/dri` выбор Intel просто даёт CPU с логом. |

### 6.1. Внедрение Intel GPU по образцу Frigate (пошагово)

Поддерживается **любая платформа Intel со встроенной графикой** (в т.ч. NUC, Celeron, Pentium). В настройках Hub выберите «Кодирование записи: Intel GPU» и пробросьте устройство в контейнер (ниже).

Эталон — [Frigate NVR](https://frigate.video/): go2rtc забирает потоки с камер, FFmpeg использует аппаратное ускорение для декодирования/кодирования. Рекомендации ниже не окончательные; документ можно дополнять.

#### Подготовка хоста (Docker host)

- Установить драйверы и проверить устройство:
  ```bash
  sudo apt update
  sudo apt install intel-media-va-driver-non-free vainfo
  sudo vainfo
  sudo ls -la /dev/dri/
  ```
  Должны быть видны `renderD128` и `card0`.

#### Настройка Docker-контейнера

- Пробросить устройство Intel GPU в контейнер (в `docker-compose` для образа с Intel):
  ```yaml
  services:
    birdlense:
      # ...
      devices:
        - /dev/dri/renderD128:/dev/dri/renderD128
        - /dev/dri/card0:/dev/dri/card0
  ```
  При необходимости добавить пользователя в группы `video` и `render` (на хосте: `getent group video render`).

#### Конфигурация FFmpeg (Intel QSV / VA-API)

- В коде, где вызывается FFmpeg для записи или обработки, добавить аргументы аппаратного ускорения:
  - **H.264:** `preset-intel-qsv-h264` (или аналог для VA-API, в зависимости от выбранного API).
  - **H.265 (HEVC):** `preset-intel-qsv-h265`.
- Во Frigate это задаётся через `ffmpeg.hwaccel_args`; у нас — через опцию в конфиге (например `recording_vaapi`) и передача соответствующих аргументов в FFmpeg при записи.

#### Интеграция с go2rtc

- Схема: go2rtc забирает потоки с камер (RTSP, ONVIF), отдаёт их приложению (например `rtsp://127.0.0.1:8554/stream_name`). Это даёт:
  - стабильные подключения к камерам (переподключения внутри go2rtc);
  - WebRTC для просмотра с низкой задержкой;
  - приложению — один локальный, предсказуемый источник.
- В настройках BirdLense: **Настройки → Видео → Go2RTC URL** (например `http://IP:1984`); имена камер (`stream_name`) должны совпадать с именами потоков в go2rtc.

#### Проверка работы GPU

- В запущенном контейнере:
  ```bash
  docker exec -it birdlense vainfo
  ```
  Должна отображаться информация о драйвере и кодеках.
- На хосте во время нагрузки:
  ```bash
  sudo intel_gpu_top
  ```

#### Типичные проблемы при внедрении

- **Регрессии при правках:** AI/редактор может удалить импорты, сломать YAML (отступы, невалидные ключи), изменить порядок операций. См. раздел «Стабильность кода» ниже.

### 6.2. Docker: безопасность, устройства и порты (без privileged и host)

**Привилегированный режим (`privileged: true`) — не использовать.** Он даёт контейнеру права, сопоставимые с хостом, отключает изоляцию и для Intel GPU не нужен. При компрометации приложения злоумышленник получит полный доступ к хосту.

**Вместо privileged:** точечная передача устройств. Для Intel GPU достаточно:
```yaml
devices:
  - /dev/dri/renderD128:/dev/dri/renderD128
```
При необходимости добавить `card0` (как в п. 6.1). Этого достаточно для аппаратного кодирования, без лишних прав.

**Host-сеть (`network_mode: host`) — только в крайнем случае.** Контейнер использует сетевой стек хоста: выше производительность, но теряется изоляция (конфликты портов, атаки бьют по хосту), не работают внутренний DNS Docker и проброс портов через `ports:`. На macOS/Windows — ограничения. Для HTTP, RTSP, WebRTC обычно достаточно bridge-режима.

**Рекомендуемый вариант:** bridge-сеть + проброс только нужных устройств и портов.

| Параметр | Privileged (плохо) | Host-сеть (осторожно) | Bridge + devices/ports (хорошо) |
|----------|--------------------|------------------------|----------------------------------|
| Безопасность | Нулевая (доступ к хосту) | Низкая (слабая изоляция) | Высокая (изоляция по умолчанию) |
| Производительность | Не влияет | Максимальная (без NAT) | Достаточная для большинства задач |
| Управление портами | Все порты хоста | Все порты хоста | Только проброшенные наружу |
| Совместимость | Везде | В основном Linux | Все платформы |

**Безопасная схема для приложения:**

1. **GPU:** только `devices` с `/dev/dri/renderD128` (и при необходимости `card0`). Без `privileged`.
2. **go2rtc, HA, ESPHome, MQTT и т.д.:** уже есть в сети — в контейнер BirdLense лишнее не тащим. Подключаемся к go2rtc по URL (Настройки → Go2RTC URL). Проброс портов 8554/1984 в compose нужен только если к go2rtc надо достучаться снаружи; для работы BirdLense достаточно доступа из сети к go2rtc по его адресу.
3. **Доступ наружу:** только нужные порты через `ports:`:
   ```yaml
   ports:
     - "8085:8080"   # BirdLense Hub
     # 8554, 1984 — только если go2rtc поднимаете на этом же хосте и нужен доступ снаружи
   ```
4. **Права процесса:** в Dockerfile создать непривилегированного пользователя и запускать приложение через `USER appuser` — дополнительный слой защиты.

**Кратко:** не использовать `privileged`; не использовать `network_mode: host` без веской причины; давать контейнеру только те устройства и порты, которые реально нужны (принцип наименьших привилегий).

### 6.3. Дополнительные рекомендации (мониторинг, FFmpeg, надёжность, безопасность)

**Контекст:** В сети уже есть всё необходимое (HA, ESPHome, go2rtc, MQTT и т.д.). В свой контейнер BirdLense лишнее не тащим — только то, что нужно для записи, детекции и веб-интерфейса. К go2rtc подключаемся по URL.

#### Мониторинг и логирование

- **На хосте:** `intel_gpu_top` (пакет `intel-gpu-tools`) — смотреть загрузку `Render/3D` и `Video` во время записи. Рост нагрузки на `Video` говорит об аппаратном кодировании.
- **В контейнере:** при сборке образа с GPU добавить `vainfo` и при необходимости периодически проверять доступность драйвера. Логи FFmpeg выводить в stdout/stderr, чтобы попадали в `docker logs`; уровень детализации в production — `-loglevel warning` или `error`.
- **Метрики:** при наличии стека (Prometheus + Grafana) можно экспортировать использование Intel GPU (например через экспортер для Intel); опционально.

#### Тонкая настройка FFmpeg для Intel QSV

- **Кодеры:** H.264 — `h264_qsv`, H.265 — `hevc_qsv`. FFmpeg должен быть собран с `--enable-libmfx` или `--enable-libvpl`.
- **Параметры:** `-global_quality 23` или `-qp` (качество); `-preset veryfast` (для GPU обычно достаточно); при необходимости `-b:v 2M`, `-g 50` (GOP / ключевые кадры для детекции).
- **Пример команды с аппаратным декодом и кодированием:**
  ```bash
  ffmpeg -hwaccel qsv -hwaccel_output_format qsv -i "rtsp://..." \
         -c:v h264_qsv -global_quality 23 -preset veryfast \
         -f mp4 /recordings/out.mp4
  ```
  `-hwaccel_output_format qsv` уменьшает копирование, оставляя данные в памяти GPU.

#### Надёжность и обработка сбоев

- **Перезапуск контейнера:** в `docker-compose.yml` указать `restart: unless-stopped`.
- **Healthcheck:** проверка работоспособности самого приложения (например HTTP-эндпоинт BirdLense), а не go2rtc — go2rtc уже в сети и управляется отдельно. Пример:
  ```yaml
  healthcheck:
    test: ["CMD", "curl", "-f", "http://127.0.0.1:8000/api/ui/health"]
    interval: 30s
    timeout: 10s
    retries: 3
  ```
- **Сбои FFmpeg/процессора:** процессор уже запускается в цикле в entrypoint; при падении он перезапускается без перезапуска контейнера.

#### Безопасность сверх базовой

- **Непривилегированный пользователь:** в Dockerfile создать пользователя и группу, переключиться на `USER appuser`. Для доступа к `/dev/dri/renderD128` добавить пользователя в группу `render` с тем же GID, что на хосте:
  ```dockerfile
  ARG RENDER_GID=107
  RUN groupadd -g $RENDER_GID render && usermod -aG render appuser
  ```
  На хосте GID можно посмотреть: `getent group render`.
- **Read-only rootfs:** если приложение пишет только в смонтированных томах, в compose задать `read_only: true` и смонтировать нужные каталоги в режиме записи (tmpfs для временных файлов при необходимости).
- **Лимиты ресурсов:** ограничить CPU и память, чтобы контейнер не исчерпывал ресурсы хоста:
  ```yaml
  deploy:
    resources:
      limits:
        cpus: '2'
        memory: 2G
  ```

#### Интеграция с go2rtc (он уже в сети)

- go2rtc не поднимаем в контейнере BirdLense — подключаемся по URL из настроек. Для записи по возможности забирать оригинальный поток (без лишнего перекодирования в go2rtc); в конфиге go2rtc можно задать несколько источников на камеру.
- Таймауты и повторы подключения к потокам настраивать в коде BirdLense под свою сеть.

#### Тестирование перед внедрением

1. **GPU в контейнере:** временный контейнер с тем же образом → `vainfo`.
2. **Тест кодирования:** короткий прогон FFmpeg вручную внутри контейнера, параллельно смотреть `intel_gpu_top` на хосте.
3. **Нагрузка:** несколько камер, убедиться в стабильности и отсутствии перегрева.

#### Обновление драйверов и библиотек

- На хосте регулярно обновлять драйверы Intel GPU и медиа-стек (libva, intel-media-driver). В образе при сборке под GPU — актуальные libva/libmfx (или libvpl).

#### Как избежать поломок при работе с AI (Cursor)

- **Версии зависимостей:** жёстко фиксировать в `requirements.txt` / `package.json`, чтобы AI не подставлял несовместимые обновления.
- **Инкрементальные изменения:** не переписывать большие куски сразу; разбивать на шаги и проверять после каждого.
- **Тесты:** хотя бы базовые юнит-тесты для ключевой логики (например формирование команд FFmpeg) — регрессии будут видны сразу.
- **Ручной review:** всегда просматривать diff перед применением.
- **Git:** перед экспериментом — коммит; откат займёт секунды.

### Стабильность кода и защита от регрессий

При доработках (в т.ч. с помощью AI) возможны непреднамеренные поломки. Рекомендации:

1. **Git — основа.** Перед экспериментами коммитить стабильную версию; при проблемах — откат.
2. **Проверять изменения.** Не принимать правки «как есть»; просматривать diff перед применением.
3. **Дробить задачи.** Давать небольшие, конкретные задания вместо общих («оптимизируй приложение»).
4. **Тесты.** Юнит-тесты и прогоны после правок снижают риск регрессии; если тесты проходят, вероятность поломки ниже.

## Рекомендуемый порядок возврата (без GPU)

Если возвращать только то, что не ломает текущую схему:

1. **Сделать сразу (низкий риск):**
   - **Перезапуск процессора без перезапуска контейнера** (п. 0) — в entrypoint запускать процессор в цикле (`while true; do ... main.py || true; sleep 2; done`). Тогда «App is UP!» естественно уходит только при старте контейнера; маркер `.startup_notify_skip` в коде уже есть как страховка.
   - nginx: убрать переменные из `proxy_pass` для `/go2rtc/` (п. 1).
   - `get_go2rtc_upstream.py`: try/except и fallback `127.0.0.1:1984` (п. 2).
   - entrypoint: обрезка `\r\n` в `GO2RTC_UPSTREAM` (п. 3).

2. **По желанию:**
   - Healthcheck в `docker-compose.yml` для проверки API (см. п. 6.3) — чтобы Docker помечал контейнер unhealthy при падении API.
   - Нефатальный health check в entrypoint (п. 3).
   - MJPEG-fallback в Live (п. 5) — если нужен обход при проблемах с go2rtc.
   - П. 7 уже выполнен (LIVE_GO2RTC в репозитории).

3. **Не трогать до повторного запуска на Intel:**
   - VA-API, Dockerfile.intel, метрики Intel GPU (п. 6).

4. **Не возвращать:**
   - Подстановку `localhost` → `172.17.0.1` (ломает host network).
   - Фоновые MJPEG-потоки по всем камерам в процессоре (риск падений и нагрузки).
