# Консилиум: инструмент сбора датасетов

Документ для обсуждения и проектирования максимально качественного и удобного инструмента сбора датасетов в BirdLense Hub.

---

## 1. Текущее состояние

### Что есть

| Компонент | Описание |
|-----------|----------|
| **Processor** | Сохраняет `best_frame` в `data/dataset/train/<Species>/` при `save_dataset_crops: true` |
| **Коррекция вида** | При исправлении в Unknowns/VideoDetails — `move_crop` или `extract_and_save_crop` (ретро) |
| **Ретроэкспорт** | Извлечение кадров из видео по bbox (frames) — только при наличии bbox |
| **Экспорт ZIP** | `train/`, `val/`, `dataset_info.json` — фильтры: период, только вручную исправленные |
| **manually_corrected** | Флаг на VideoSpecies — защита от перезаписи при перегенерации треков |

### Потоки данных

```
Запись видео → YOLO+ByteTrack → best_frame → dataset_saver → train/Species/video_id_track_id_index.jpg
                    ↓
              VideoSpecies (species, frames, confidence) — создаётся после API
                    ↓
         Unknowns / VideoDetails → коррекция/подтверждение → manually_corrected=True
                    ↓
         move_crop (если файл есть) ИЛИ extract_and_save_crop (ретро)
                    ↓
         Экспорт ZIP → Colab / дообучение
```

**Форматы имён файлов (текущие):**
- **Processor:** `video_id_track_id_index.jpg` — index = порядковый номер в списке детекций (0, 1, 2…)
- **Retro:** `video_id_track_id_vs.id.jpg` — vs.id = VideoSpecies.id из БД

### Известные проблемы (из опыта)

1. **Старые фото не кропнуты** — ретроэкспорт без bbox давал полный кадр → исправлено: пропуск при отсутствии bbox
2. **Неправильные названия** — YOLO ошибается → опция «только вручную исправленные»
3. **Ручная разметка портилась** — перегенерация треков удаляла всё → `manually_corrected` защищает
4. **Разные форматы имён** — processor vs retro используют `video_id_track_id_{index|vs.id}.jpg` — move_crop ищет по `video_id_track_id_*`

## 2. Цели качества датасета

### Критерии качества

| Критерий | Описание | Как достичь |
|----------|----------|-------------|
| **Правильность вида** | Каждый crop помечен верным видом | Ручная проверка, только manually_corrected |
| **Качество кадра** | Резкий, птица в кадре, не обрезана | best_frame по blur+size, bbox-кроп |
| **Разнообразие** | Разные ракурсы, освещение, особи | Не дедуплицировать слишком агрессивно. Автодедупликация — вне scope |
| **Баланс классов** | Не перекос в сторону частых видов | Мониторинг, предупреждения |
| **Формат** | YOLO cls: train/Species/img.jpg | Единый _sanitize_dirname |

### Метрики для мониторинга

- Количество crops по виду (гистограмма)
- Доля manually_corrected от общего
- Количество «Unknown» / низкокачественных
- Пропущенные при ретро (no bbox, no file)

## 3. Персонажи и сценарии

### Персонаж A: «Быстрый сбор»

**Цель:** Накопить много кадров для дообучения, не тратя время на проверку.

**Действия:**
- Включить `save_dataset_crops`, `dataset_min_confidence` 0.5–0.6
- Периодически экспортировать ZIP
- Минимум ручной работы

**Риск:** Много шума (неправильные виды, размытые кадры).

**Нужно:** Фильтр по confidence при экспорте (доп. к dataset_min_confidence процессора), предпросмотр статистики перед экспортом.

---

### Персонаж B: «Качество важнее количества»

**Цель:** Только проверенные кадры для fine-tune.

**Действия:**
- Unknowns → исправить все сомнительные
- VideoDetails → проверить и исправить при необходимости
- Ретроэкспорт с «только вручную исправленные»
- Экспорт с «только вручную исправленные»

**Риск:** Медленно, мало данных на редкие виды.

**Нужно:** Удобный workflow проверки, прогресс «проверено N из M».

---

### Персонаж C: «Целевой сбор»

**Цель:** Улучшить модель по конкретным видам (синицы, воробьи, сойка).

**Действия:**
- Фильтр по виду в Unknowns / Timeline
- Ретроэкспорт за период с фокусом на вид
- Экспорт только выбранных видов

**Нужно:** Фильтр по виду при экспорте, отчёт «по видам».

---

### Сценарий D: «Очистка» ✅ (реализовано)

**Цель:** Удалить мусор из датасета (full-frame, осиротевшие файлы).

**Реализовано:** Кнопка «Очистить датасет» в Library → Датасет:
- **Full-frame по эвристике:** размер >800×600 и aspect 16:9 или 4:3 — удаляются
- **Осиротевшие:** опционально — файлы без VideoSpecies (video_id, track_id). *Риск:* processor-файлы до синхронизации.

См. [DATASET_CROPS_ONLY_CONCILIUM.md](./DATASET_CROPS_ONLY_CONCILIUM.md).

## 4. Предложения по улучшению

| 2 | **Предпросмотр перед экспортом** | «Будет экспортировано: 156 crops, 12 видов. 89 вручную проверенных.» — кнопка «Скачать» |

### Фаза 2: Качество и фильтры (средняя сложность)

| # | Улучшение | Описание |
|---|-----------|----------|
| 5 | **Фильтр по виду при экспорте** | Мультиселект видов: экспортировать только Parus major, Cyanistes caeruleus и т.д. |
| 6 | **Минимум crops на вид** | При экспорте: исключить виды с < N кадров (настраиваемо) |

## 5. Рекомендуемый приоритет

### Зависимости

- **Confirm (#7)** — желательно до или вместе с **Дашбордом (#5)**, иначе «доля проверенных» неполная
- **Val split (#9)** — логично вместе с **Предпросмотром (#2)**, чтобы показывать распределение train/val
- **Предпросмотр** — зависит от маппинга файлов↔БД (см. риски)

### Быстрые победы (1–2 дня)

1. **Подсказки** — уточнить текст «Только вручную исправленные», добавить help
2. **Предпросмотр экспорта** — `GET /api/ui/dataset/export/preview` → `{total, by_species, manually_corrected_count}`. *Ограничение:* для processor-файлов маппинг на VideoSpecies по (video_id, track_id) — manually_corrected_count может быть приблизительным
3. **Раздел «Датасет»** — выделить секцию в Storage Management (или отдельная страница). *Оценка:* 2–3 дня при переносе навигации

### Средний приоритет (≈ неделя)

4. **Подтверждение (confirm)** — кнопка «Верно» в VideoDetails/Unknowns → `manually_corrected=True`
5. **Дашборд** — блок статистики: crops по виду, доля проверенных
6. **Val split** — при экспорте создавать val/ с 20% по video_id. *Учёт:* фильтры (период, only_manually_corrected)
7. **Фильтр по confidence при экспорте** — параметр `min_confidence` в API экспорта

### Долгосрочно

8. **Режим разметки** — отдельный UI для быстрой проверки
9. **Фильтр по виду** — мультиселект при экспорте

## 6. Технические решения

### Формат имён файлов (текущий)

| Источник | Формат | Связь с БД |
|----------|--------|------------|
| **Processor** | `video_id_track_id_index.jpg` | index = enumerate (0,1,2…). Связь с VideoSpecies только по (video_id, track_id) |
| **Retro** | `video_id_track_id_vs.id.jpg` | vs.id = VideoSpecies.id — прямая связь |

**move_crop** ищет `video_id_track_id_*`, требует `len(matches)==1` (иначе не двигает).

**Рекомендация:** Оставить как есть. Унификация на `vs.id` потребовала бы: processor получает vs.id от API после создания VideoSpecies — усложнение пайплайна. Риск коллизии низкий: processor и retro редко создают оба файла для одного (video_id, track_id).

### Val split

**Текущее:** Только train/. Val пустой.

**Рекомендация:** При экспорте — split по **video_id** (не по файлу). Все crops одного видео — в одном сплите (избегаем data leakage). Детерминированно: `hash(video_id) % 5 == 0` → val, иначе train. Учитывать фильтры: период, only_manually_corrected, min_confidence.

### dataset_info.json

Расширить:
```json
{
  "created_at": "...",
  "train": {"Parus major (Great Tit)": 45, ...},
  "val": {"Parus major (Great Tit)": 12, ...},
  "total_images": 120,
  "manually_corrected_count": 89,
  "filters": {"start_date": "2024-03-01", "end_date": "2024-03-15", "only_manually_corrected": true}
}
```

## 7. Риски и ограничения

| Риск | Описание | Митигация |
|------|----------|-----------|
| **Предпросмотр неточен** | Processor-файлы не имеют vs.id — manually_corrected_count по (video_id, track_id) приблизительный | Явно помечать «приблизительно» в UI |
| **Осиротевшие файлы** | После reject, смены вида — файл может остаться в старой папке | Опция «Очистить датасет»: удалить файлы без соответствующего VideoSpecies (осторожно) |
| **Конфликты при collaborative** | Два пользователя правят один crop | Отложено до Фазы 4; при необходимости — блокировки/версии |

## 8. Вне scope (отложено)

- **Автоматическая дедупликация** — по хэшу/визуальной близости; критерии неочевидны
- **Collaborative labeling** в первой версии — см. Фаза 4
- **Миграция формата имён** — при унификации потребуется скрипт миграции; пока не планируется
- **Дообучение на сервере** — требует GPU, отдельная инфраструктура
