У многих любителей природы и владельцев участков рано или поздно появляется камера на кормушке или скворечнике. Дальше типичный путь: либо проприетарное облако с подпиской и непрозрачной обработкой, либо самодельная связка из NVR + скриптов, которая быстро превращается в хрупкий зоопарк сервисов.

Хочется другого: **чтобы видео и метаданные жили у вас**, чтобы распознавание можно было **докрутить под свой регион**, и чтобы стек нормально дружил с уже привычными инструментами умного дома — Frigate, MQTT, Home Assistant, Telegram.

В этой статье разберу **BirdLense Hub** — открытый проект, который мы развиваем как «один контейнер + вокруг экосистема»: компьютерное зрение на YOLO, трекинг, запись роликов, веб-интерфейс с таймлайном и мост к citizen science. Это не обзор «лучшей облачной камеры», а инженерный разбор того, **как устроен конвейер** и **где границы** такого решения.

## Что это за проект

**BirdLense Hub** — ПО для мониторинга кормушки / сада: на видеопотоке ищет птиц (и отдельно учитывает белок), классифицирует виды локальной моделью, пишет короткие клипы, строит таймлайн и отчёты. Ключевая идея — **основная обработка на вашей машине** (типично x86 + Docker), без обязательной отдачи кадров стороннему API.

Репозиторий: **https://github.com/Gfermoto/BirdLense-Hub** (перед публикацией сверьте номер релиза с корневым файлом **`VERSION`** и тегами на GitHub).  
Документация на GitHub Pages (MkDocs): **https://gfermoto.github.io/BirdLense-Hub/** — там же баннер версии и интерактивный OpenAPI (Redoc).

Ниже — как это устроено внутри, без маркетинговых обещаний «распознает всё идеально»: качество зависит от света, угла, модели и того, насколько ваши виды покрыты обучающими данными.

## Архитектура: один контейнер и всё вокруг

В центре — **один Docker-контейнер**, в котором собраны:

- **nginx** — раздаёт статический React UI, проксирует API и служебные пути;
- **Flask (gunicorn)** — HTTP API (`/api/...`), в том числе UI-роуты и интеграции;
- **processor** — отдельный процесс пайплайна: чтение потока, инференс, запись видео, спектрограммы, MQTT;
- опционально **MCP** — чтобы внешние клиенты могли вызывать API по контракту.

Снаружи контейнера обычно живут привычные вещи:

- **Go2RTC** — универсальный шлюз RTSP / WebRTC / HLS (рекомендуется как источник кадров);
- **MQTT-брокер** — события Frigate, BirdNET, ESPHome;
- по желанию **Frigate** с Bird Classification;
- **BirdNET** (BirdNET-Pi / Go и т.п.) для аудио.

Такое разделение осознанное: Go2RTC и MQTT у многих уже есть в инфраструктуре умного дома, а Hub фокусируется на **записи, ML и UI**.

Упрощённая схема потока видео:

1. Processor подключается к потоку Go2RTC.  
2. Срабатывает триггер (движение OpenCV, событие Frigate, MQTT, ESPHome — в зависимости от конфигурации).  
3. Запускается запись клипа на диск (`data/recordings/...`).  
4. **YOLO** отвечает за детекцию «птица / белка» и классификацию вида; **ByteTrack** помогает связать объекты между кадрами.  
5. Метаданные и пути к файлам уходят в API; UI показывает таймлайн, карточки видео, виды, «неизвестные» и т.д.

Отдельный сценарий — **слияние с Frigate**: из MQTT приходят события с `sub_label` от Bird Classification (виды из iNaturalist taxonomy), и Hub использует это при агрегации результатов. Параллельно **BirdNET** по MQTT даёт аудио-детекции; их можно сливать с видео по временному окну.

Если нужны детали по портам и маршрутам — в репозитории есть `docs/ARCHITECTURE.ru.md` с блок-схемой.

## Модели и «европейский» vs «американский» контекст

В проекте разделены две роли модели:

1. **Детектор** (бинарно: птица или белка в кадре) — отдельный этап.  
2. **Классификатор видов** — отдельные веса, их можно менять под регион.

Сейчас в типичной поставке активна **EU-ориентированная** классификация порядка **~491 вида** (объединение birds-525 и iNaturalist для Европы). Для США исторически использовался контур **NABirds**; веса могут лежать как резерв (`best_US.pt` и т.п.) — см. README репозитория и `docs/TRAINING.md` / `docs/DATASETS.md`, если захотите дообучить или пересобрать датасет.

Практический вывод для читателя: **«из коробки» качество сильно коррелирует с тем, насколько ваши птицы похожи на то, на чём учили классификатор**. Для редких локальных форм и сильного смещения камеры без дообучения ждать чудес не стоит — зато стек **прозрачен**: можно экспортировать кропы, править разметку, гонять свой train pipeline (в доках есть Colab-ориентированные материалы).

## Интерфейс и «продуктовые» фичи

Помимо таймлайна и просмотра клипов, в UI и API есть вещи, которые обычно интересны именно «домашним орнитологам» и интеграторам:

- фильтры по дате и **времени суток** (утро / день / вечер / ночь);  
- раздел **«Неизвестные»** для низкой уверенности и ручной правки;  
- **экспорт** CSV/JSON, **eBird**-чеклист, **PDF**-отчёт за месяц;  
- сравнение наблюдаемых видов с **региональной статистикой eBird** (в Overview);  
- **iNaturalist**: кроп для выгрузки наблюдения;  
- **Xeno-canto** — ссылки на записи песен на странице вида;  
- **календарь миграций** по месяцам для выбранного вида;  
- **Prometheus**-метрики (`/metrics`, `/api/metrics`) для Grafana;  
- **Telegram**-уведомления с превью кадра;  
- управление **кормушкой** через MQTT / ESPHome по детекции;  
- **PWA** для установки веб-интерфейса как приложения.

Это не значит, что всё нужно каждому — но набор опций отражает реальный запрос: **не только «увидел синицу»**, но и **учёт, отчёты, интеграции и экспорт в научно-любительские платформы**.

## Приватность и границы ответственности

Кадры и база SQLite лежат у вас в `data/`. Это плюс к приватности и к юридической простоте в быту — но накладывает на вас же вопросы **безопасности хоста**, бэкапов и того, **куда вы потом выгружаете экспорт** (eBird / iNaturalist — уже публичные действия).

Про уязвимости и контакт для responsible disclosure — в корневом `SECURITY.md` репозитория.

## Ограничения честно

Кратко, кому может **не** зайти такой стек:

- нужен **полностью готовый SaaS «в один клик»** без Docker и без чтения доков;  
- нет железа под инференс (CPU часто возможен, но с ожиданиями по latency; GPU — по конфигурации);  
- ожидание **идеальной таксономии** без настройки порогов и без работы с «неизвестными»;  
- камера даёт только смазанный ночной силуэт — CV здесь не волшебство.
