# Промт: План подготовки BirdLense Hub к публикации как open-source проект

## Контекст проекта

**Проект:** BirdLense Hub — система мониторинга птиц для фидеров, садов и полевых установок
**Текущее состояние:**
- Репозиторий содержит 208+ Markdown файлов (77 на русском, остальные на английском)
- 154 файла документации в `/docs`
- 440 скриптов в `/scripts`
- 10 Docker Compose файлов (включая примеры) в `/app`
- Существующий `install.sh` в корне репозитория
- Настроенные GitHub Actions workflows (CI/CD, CodeQL, Docker publish, Docs Pages)
- MkDocs для генерации сайта документации

**Цель:** Подготовить проект к публикации как международный open-source проект

---

## Задачи для планирования

### 1. Аудит и консолидация документации

**Проблема:** Избыточная документация (154 файла в `/docs`), дублирование контента, смешение внутреннего жаргона с пользовательскими инструкциями

**Требуется:**
1.1. Классифицировать все документы по категориям:
   - **Пользовательские** (установщики, конфигурация, использование)
   - **Контрибьюторские** (разработка, тесты, CI/CD)
   - **Внутренние** (roadmap, аудиты, планы разработки, история решений)
   - **Архивные** (устаревшие, исторические)

1.2. Предложить структуру консолидации:
   - Какие документы объединить (например, множественные ML-гайды)
   - Какие документы переместить в `/docs/archive/` или удалить
   - Целевое количество документов после очистки (рекомендация: ≤50 основных)

1.3. Создать карту навигации:
   - Единый `/docs/README.md` как точка входа
   - Логическая группировка по разделам (Getting Started, Configuration, Development, etc.)
   - Стратегия i18n: EN как основной, RU как опциональное зеркало

1.4. Ревизия конкретных файлов:
   - `/docs/article/` — оценить релевантность для внешних пользователей
   - `/docs/github-issues/` — переместить во внутренний архив
   - `/docs/project/` — консолидировать с корневыми файлами
   - Benchmark JSON файлы в корне — переместить или удалить

### 2. Очистка репозитория от артефактов

**Проблема:** Беспорядок из устаревших и избыточных файлов

**Требуется:**
2.1. Docker-файлы (сейчас 10 файлов в `/app`):
   ```
   docker-compose.stack.example.yml
   docker-compose.nvidia.example.yml
   docker-compose.host.example.yml
   docker-compose.intel.example.yml
   docker-compose.pull.yml
   docker-compose.image.yml
   docker-compose.yml
   docker-compose.override.example.yml
   docker-compose.dev-split.example.yml
   ```
   - Определить минимальный набор для пользователей
   - Предложить схему именования (например, один основной + профили через `.env`)
   - Удалить или переместить в `/examples/docker/` избыточные примеры

2.2. Скрипты (440 файлов в `/scripts`):
   - Выделить пользовательские скрипты (должны быть в репо)
   - Выделить внутренние/dev-скрипты (переместить в `/scripts/internal/` или удалить)
   - Jupyter notebooks (`birds_train.ipynb`, etc.) — оценить необходимость
   - Benchmark scripts — оставить только если полезны контрибьюторам

2.3. Корневые файлы:
   - Benchmark JSON файлы — удалить или переместить
   - `MANUAL_INTERVENTION_REQUIRED.md` — внутреннее, удалить/архивировать
   - `PRODUCTION_READINESS*.md` — консолидировать или архивировать
   - `.pending-changes.md` — удалить
   - Файл с именем `'0,x[video],raw,x[raw_track_count])'$'\n''PY'` — удалить

2.4. Предложить обновления для `.gitignore`:
   - Паттерны для временных файлов
   - Исключения для dev-артефактов

### 3. Интерактивный скрипт развёртывания

**Текущее состояние:** Есть `./install.sh` с базовой функциональностью

**Требуется улучшить:**
3.1. Функциональность скрипта:
   - [ ] Детекция ОС (Linux/macOS) и архитектуры (x86/ARM)
   - [ ] Проверка и установка зависимостей (Docker, Docker Compose, curl, openssl)
   - [ ] Интерактивный режим с вопросами:
     - Порт для UI (дефолт 8085)
     - Путь для данных (дефолт `./data`)
     - Тип GPU (CPU/NVIDIA/Intel/OpenVINO)
     - Нужен ли pull готового образа vs локальная сборка
   - [ ] Создание `.env` с безопасными секретами (генерация PROCESSOR_SECRET, FLASK_SECRET_KEY)
   - [ ] Копирование шаблона конфигурации (`minimal.yaml` → `user_config.yaml`)
   - [ ] Запуск стека и verification (health checks)
   - [ ] Вывод следующей шаги (как настроить камеры, Go2RTC)

3.2. Дополнительные режимы:
   - `--pull` — использовать pre-built образ (уже есть)
   - `--build` — локальная сборка (уже есть)
   - `--uninstall` — очистка (контейнеры, volumes, сеть)
   - `--update` — обновление до последней версии
   - `--backup` — бэкап конфигурации и данных перед обновлением
   - `--restore` — восстановление из бэкапа
   - `--dry-run` — показать что будет сделано без выполнения

3.3. Безопасность:
   - Генерация криптографически стойких секретов
   - Проверка прав доступа (не запускать от root без предупреждения)
   - Валидация входных параметров
   - Логирование действий (с возможностью отключения)

3.4. Документация скрипта:
   - Help message (`--help`)
   - Примеры использования в README
   - Troubleshooting section

3.5. Тестирование:
   - Сценарии для чистой установки
   - Сценарии для обновления
   - rollback механизм

### 4. Финальные требования к плану

**Формат вывода:**
```markdown
# План подготовки BirdLense Hub к open-source публикации

## Фаза 1: Аудит (неделя 1)
- Задачи...
- Критерии завершения...

## Фаза 2: Очистка (неделя 2)
...

## Фаза 3: Улучшение install.sh (неделя 3)
...

## Фаза 4: Финализация документации (неделя 4)
...

## Чеклист готовности к публикации
- [ ] Нет IP, hostname, путей специфичных для текущего инсталла
- [ ] Нет токенов, паролей, API keys (даже замаскированных)
- [ ] README на английском — понятен международной аудитории
- [ ] CONTRIBUTING.md и CODE_OF_CONDUCT.md есть
- [ ] SECURITY.md (корень) — как сообщать об уязвимостях
- [ ] LICENSE корректен
- [ ] Все тесты проходят
- [ ] install.sh работает на clean OS
```

**Критерии качества плана:**
- Каждая задача имеет четкий критерий завершения (Definition of Done)
- Указаны приоритеты (Critical/High/Medium/Low)
- Оценена трудоемкость (часы/дни)
- Выявлены зависимости между задачами
- Предложены конкретные команды для удаления/перемещения файлов
- Для install.sh — пошаговый план улучшения с примерами кода
